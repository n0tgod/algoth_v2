# algoth v2 — парный трейдинг на крипто-перпах

Исследовательский стенд и торговый движок для стат-арбитража на бессрочных фьючерсах.

**Текущая фаза: A — исследование.** Задача этой фазы одна: честно ответить, существует ли устойчивый эдж, до того как написана хоть строчка торгового бота. Отрицательный ответ — такой же полноценный результат, как положительный, и стоит он на порядок дешевле.

---

## Что это

Система торгует не направление рынка, а **отношения между активами**: покупает один инструмент, продаёт другой, зарабатывает на возврате спреда к среднему. Базовая единица — не сделка, а **позиция** из двух ног, которая открывается и закрывается только целиком.

Проект не является продолжением первой версии платформы. Из неё переиспользуются идеи, отдельные компоненты (таблица maintenance margin Binance, SQL взвешенных корзин) и — главное — понимание, почему она не сработала.

## Порядок фаз

| Фаза | Капитал | Что доказывает |
|---|---|---|
| **A. Исследование** | $0 | Есть ли эдж. Бэктест, walk-forward, статистическая валидация |
| B. Paper trading | $0 | Инженерная корректность на живых данных |
| C. Живой микро | $1–2k | Реальные исполнения, проскальзывание, funding, нештатные ситуации |
| D. Масштаб | $10–20k | Здесь живые результаты становятся статистически осмысленными |
| E. Упаковка | — | Продукт с реальным треком за спиной |

Решение «работает или нет» принимается на фазе A. Если она закрывается отрицательно, фаз B–D не будет.

## Запуск: окружение

Этапы A0–A1 обходятся стандартной библиотекой — так и задумано, сборщики должны запускаться на голом сервере. **Начиная с A2 нужны зависимости**, и системный `python3` их не имеет:

| Этап | Что нужно |
|---|---|
| A0, A1 | стандартная библиотека |
| A2 | `pyarrow` |
| A3, A4, R1+ | `duckdb`, `numpy` |
| B1 (сбор стакана) | `websocket-client` |

Окружение создаётся один раз и живёт рядом с репозиторием:

```bash
cd ~/algoth_v2
[ -d .venv ] || python3 -m venv .venv
.venv/bin/pip install -q numpy pyarrow duckdb websocket-client
```

Дальше **все прогоны идут через `.venv/bin/python`, а не через `python3`**:

```bash
.venv/bin/python research/r1_factor/premise.py --interval 1m
```

Команда идемпотентна: если окружение уже есть, `venv` не пересоздаётся, а `pip` ничего не доставляет. Проверка на месте:

```bash
.venv/bin/python -c "import numpy, duckdb, pyarrow, websocket; print('зависимости на месте')"
```

Отчёты — исключение и зависимостей не требуют: все числа лежат в JSON-артефактах прогонов, поэтому `report.py` собирается любым `python3`.

## Запуск: сбор живых данных

Сборщик стакана — не прогон: он живёт неделями и ничего не публикует, а
пишет ряды на диск. Поэтому запускается не через `tools/run.sh`:

```bash
cd ~/algoth_v2
nohup .venv/bin/python research/b1_book/collect.py \
  --symbols BTCUSDT,ETHUSDT,SOLUSDT,XRPUSDT,DOGEUSDT,ARBUSDT,LINKUSDT,AVAXUSDT \
  --raw ARBUSDT \
  > research/b1_book/out/collect.log 2>&1 &
```

Проверить, что он не молчит впустую:

```bash
tail -f ~/algoth_v2/research/b1_book/out/collect.log     # строка раз в минуту
cat ~/algoth_v2/research/b1_book/out/status.json         # состояние книг
du -sh ~/algoth_v2/research/b1_book/out/                 # сколько занял
```

Перед первым запуском — проверка пути записи без сети:

```bash
.venv/bin/python research/b1_book/collect.py --selftest
```

Ряды в git не идут (как свечи и funding): публикуются только отчёты.

## Запуск: прогон и публикация одной командой

Прогон идёт на сервере, а обсуждается в другом месте, поэтому результат должен оказываться в git сам. `tools/run.sh` берёт сообщение для коммита и обычную команду прогона:

```bash
cd ~/algoth_v2
tools/run.sh "T1: поглощение с перевесом" \
  research/t1_tape/probe.py --symbols BTCUSDT,ETHUSDT --start 2025-03-03
```

Что она делает и почему именно так:

- **отвязывается от ssh** — обрыв связи прогон не убивает, `nohup` писать не нужно;
- **зовёт `.venv/bin/python`** — системный не имеет зависимостей, и прогон R1 однажды упал на сервере ровно этим;
- **публикует только при успехе** — упавший прогон оставляет недописанный артефакт, и публиковать его значит предъявить обрывок как результат;
- **пишет журнал** в `<этап>/out/<скрипт>.log` и печатает путь к нему.

Проверить ход прогона (путь полный, работает из любого каталога):

```bash
tail -f ~/algoth_v2/research/t1_tape/out/probe.log
pgrep -af probe.py || echo "процесса нет"
```

`tools/publish.sh` остаётся отдельной командой для случая, когда прогон уже сделан и надо опубликовать его артефакты руками.

## Исследования

### `research/a0_venue_inventory` — инвентаризация площадок ✅

Фактические размеры универсумов, глубина публичной истории, доступность данных. Отчёт: [`out/A0-report.md`](research/a0_venue_inventory/out/A0-report.md).

Ключевые результаты:

- рабочий универсум — **721 базовый актив** на пересечении Bybit и Binance
- глубина истории: 4+ года у 99 активов, 3+ года у 174, 2+ года у 268
- **30.5 % USDT-перпов Bybit уже делистнуты**, медианный срок жизни 436 дней, темп растёт

Последний пункт продиктовал требование определять универсум **на момент времени**: отбор активов «у которых на сегодня есть N лет истории» — это отбор выживших.

Запуск:

```bash
cd research/a0_venue_inventory
python3 inventory.py      # сбор, только стандартная библиотека, кэш на диске
python3 report.py         # отчёт из собранных данных
```

Сбор данных Bybit требует запуска оттуда, где доступен `api.bybit.com`.
