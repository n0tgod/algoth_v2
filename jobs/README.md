# Очередь заданий

Сессия кладёт сюда файл `<имя>.job`, сервер его выполняет и публикует
результат в `done/<имя>.log`. Прямого доступа к серверу у ассистента
нет (наружу открыты только 80 и 443), а открывать исполнение по HTTP
рядом с ключами биржи — плохой обмен: канал через git даёт ту же
пользу, аутентификацию доступом к репозиторию и аудит самой историей.

Формат — одна строка:

```
run research/probe_turn/turn.py --tag 1m
restart-book
status
```

Правила исполнения (`tools/jobs.sh`, проверки `tools/test_jobs.sh`):

- запускается ТОЛЬКО питон-файл из репозитория (`research/…`,
  `tools/…`) и только три объявленных действия;
- аргументы проверяются посимвольно, `eval` не используется вовсе:
  `;`, `$(…)`, кавычки и пробелы-инъекции отвергаются;
- выполненное задание помечается `done/<имя>.done` и не повторяется —
  маркер в git, поэтому переживает перезапуск сторожа;
- расхождение дерева с `origin/main` останавливает очередь: молча
  перематывать незапушенную работу нельзя;
- прогон идёт фоном с пониженным приоритетом, в git уходит хвост лога.

## Мгновенный подхват

Сторож смотрит очередь раз в пять минут — это страховка. Обычный путь
быстрее: после публикации задания сессия дёргает сигнал

```
GET /jobs-poke?k=<ключ страницы>
```

и сервер смотрит очередь сразу же (ответ `{"ok": true}`). Сигнал не
несёт ни команды, ни аргумента: он лишь запускает тот же
`tools/jobs.sh`, что и сторож. Поэтому утечка ключа страницы не даёт
исполнения — она даёт право попросить сервер перечитать наш же git.
Чаще раза в 10 секунд сигнал отвечает отказом по частоте: открытый в
сеть путь не должен превращаться в непрерывный `git fetch` рядом с
живым сбором.
