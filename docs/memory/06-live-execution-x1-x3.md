- **X1 начат: venue-клиент Bybit V5 и команда `bot probe` — первый код проекта, умеющий ставить заявку.** `bot/src/venue.rs`: подпись HMAC-SHA256 по V5 (timestamp + key + recv_window + payload), POST подписывает РОВНО ту строку, что уходит на провод (подпись по пересобранному словарю однажды разошлась бы с телом запроса); часы синхронизируются по середине запроса; кошелёк UNIFIED, позиции, открытые заявки, лучшие цены, постановка/отмена лимитки (Limit, IOC/PostOnly, orderLinkId, reduceOnly), исполнения. Подпись закреплена тестом ЧИСЛОМ, посчитанным независимо (python hmac), отрицательный контроль с переставленными полями кусается. Количество и цена едут строками — округление по шагам инструмента из `research/a1_universe/out/instruments.json` остаётся вызывающему коду

Ключ живёт ТОЛЬКО на VPS в `~/.bybit/live.env` (режим 600, 79 байт, проверено владельцем), `.gitignore` получил `*.env`; файл с ключом из переписки перезаписан случайными байтами и удалён. **Testnet `api-testnet.bybit.com` отвечает с VPS 200** — X1 гоняется против тестовой сети, база URL у команды параметром, код один при любой базе

- **Решение владельца: testnet не используется, X1 проверяется сразу на живом счёте.** Довод по существу верен и записан в спеку 12 §8: у testnet Bybit отдельные аккаунты и отдельные ключи — прогон против него проверял бы не тот ключ и не тот счёт, а curl-двухсотка доказала только сеть, не авторизацию. Порядок на живом счёте обязательный: сперва `bot probe` только на чтение (заявок не ставит вовсе), затем круг «поставил-снял» — PostOnly-лимитка BTCUSDT на 20 % ниже бида, которая не может исполниться по построению (PostOnly пересекающую книгу заявку отвергает, а не исполняет). Единственная защита, работающая при любом дефекте кода, — права ключа: только торговля, без вывода; владельцу предложено также привязать ключ к IP сервера в настройках Bybit

- **X1 закончен: живой исполнитель `bot live` (`bot/src/live.rs`), 14 интеграционных тестов на подставной бирже, всего в ядре 47.** Исполнитель НЕ решает ничего — он превращает уже записанные решения сканера (`entries_live/exits_live.jsonl`, строки разбора) в заявки: вход и принудительные выходы — IOC-лимит с потолком цены (30 б.п. от середины, стоп 100 б.п.), цель — лежащая GTC reduceOnly-лимитка НА УРОВНЕ ОБЕЩАНИЯ с момента входа (первая живая проверка правила v13; уровень от цены СОБЫТИЯ, не нашего исполнения). Размер — floor к шагу лота от ноги 30 $ (вверх нельзя — потолок забора); нога мельче минимального лота — честный отказ без заявки (BTC при 30 $ неторгуем — минимум 0.001 BTC). Журнал write-ahead тем же форматом, что у тени, но СВОЙ каталог (`bot/out/live`) — живые 300 $ и бумажные 3000 в одном журнале обессмыслили бы сверку
- **Сверка §4 на каждом такте, и порядок такта выведен тестом, а не рассуждением: обнаружение исполнившихся целей идёт ДО сверки.** Лежащая лимитка законно исполняется между тактами и снимает позицию на бирже раньше, чем журнал об этом узнал; сверка первой кричала бы «расхождение» на каждом тейке — поймано тестом до первого живого прогона. Расхождение с биржей — остановка БЕЗ закрытий (своё состояние уже неверно, автоматика на нём запрещена; снимаются только свои лежащие цели). Остальные остановки §5 (день −15 $, итог −45 $, три отказа подряд, тишина цикла 3 ч) закрывают позиции reduceOnly-IOC: позицию без работающего сканера не управляет никто. **После файла KILL не совершается НИЧЕГО — ни заявок, ни отмен**
- Книга записала «дошла до цели», а лимитка на бирже не исполнилась — расхождение правила v13 уезжает в причину закрытия СЛОВАМИ и закрывается IOC: главный замер X3 не теряется молча. Перезапуск: количество позиции берётся у БИРЖИ (журнал держит состав, биржа — точные числа), решение без исхода закрывается отказом «оборвано перезапуском» — вход привязан к секунде события, исполнять его позже значит торговать прошлое. Дедуп событий входа переживает закрытие позиции и закреплён тестом (пока имя в позиции, снятый дедуп маскируется проверкой «имя уже в позиции» — первый отрицательный контроль прошёл мимо и тест переписан на сценарий после закрытия). Три отрицательных контроля кусаются: дедуп, снятая постановка цели, слепая сверка
- **Сухой прогон X2 — не выдуманные исполнения, а несостоявшиеся заявки:** `--dry` формирует заявку по живому справочнику (шаги цены и объёма с площадки, `venue.instrument`), печатает её словами в Reject и не отправляет; позиций в сухом прогоне не существует. Запуск — `tools/run_live.sh` (по умолчанию сухой; `--live` — X3; `--stop`; `--clear-halt` после разбора причины остановки; аварийно — `touch bot/out/live/KILL`). База URL обязательна словом в команде — живой счёт не зависит от чьего-то умолчания

- **Первый сухой прогон X2 на сервере вскрыл дефект первого запуска, ради которого X2 и существует: вся история событий книги выглядела новыми решениями.** Файл `entries_live.jsonl` перечитывается целиком, журнал исполнителя на первом запуске пуст — сотни старых входов шли в обработку по два запроса к бирже на каждый (владелец увидел это как «live_status.json за полминуты не появился»: первый такт обходил историю минуты). В сухом прогоне это шум, **в живом первые шесть исторических событий открыли бы настоящие позиции по прошлым сигналам**. Правило: событие входа старше `stale_entry_sec = 120 с` не торгуется, не трогает биржу и не порождает ни строки журнала — вход привязан к секунде события, исполнять его позже значит торговать прошлое; число пропущенных видно в статусе (`stale_entries_skipped`). **Выходы порогом не гасятся никогда: вход — возможность, выход — обязанность перед открытой позицией.** Тест двусторонний (старое молчит, свежее рядом входит), отрицательный контроль со снятым порогом кусается
- Попутно: `tail -30 файл1 файл2` — устаревший синтаксис GNU tail, при нескольких файлах он падает «option used in invalid context»; в командах владельцу писать `tail -n 30`

- **Второй заход X2: журнал первого прогона оказался сломан моим же дефектом, и новый исполнитель честно отказался на нём подниматься («номер 125 вне очереди»).** Decision писался с МЕТКОЙ СОБЫТИЯ, а ротация журнала режет строки на суточные файлы по `at_ms` — исторические события разложили записи по файлам 14–21 августа, и номера строк перемешались между сутками (Decision в старый файл, его же Reject — в сегодняшний). Правка: **журнал штампуется моментом ЗАПИСИ**, секунда события едет отдельным полем `src_ts` (то же различие, что «час — ключ листа, не время сделки»); дедуп событий — по `src_ts`. Поле опциональное и в журнале тени не появляется — паритет не тронут. Регрессия закреплена полуночным тестом (свежее событие за секунды до полуночи не рвёт журнал), отрицательный контроль воспроизводит серверный отказ дословно («строки разъехались по суткам»)
- Там же: остановленный исполнитель печатал строку каждые 5 секунд — тревога, повторяющаяся вечно, перестаёт быть сигналом; теперь состояние печатается при СМЕНЕ. Сломанный журнал первого прогона — только сухие Decision/Reject без единой позиции и без денег; лечение — отставить каталог `bot/out/live` в архив и начать чистый (команда дана владельцу). Сами сформированные заявки первого прогона верны: ноги ровно ~30 $, цены у рынка, у каждой цель уровнем — механика формирования подтверждена
- Попутная находка первого прогона: **отказов подряд может быть больше порога** («4 отказов подряд» при пороге 3) — проверка серии стоит в конце такта, и несколько отказов одного такта успевают накопиться; на вердикт не влияет (остановка случилась), но число в сообщении читается странно. Источник серии — исторические имена, которых нет в справочнике; с порогом свежести класс исчезает
