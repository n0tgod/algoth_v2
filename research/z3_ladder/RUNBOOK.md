# Z3 — лесенка ценовых уровней

## Зачем, если есть Z2

Z2 меряет снятие заявок по **полосе ±0.25 %, привязанной к середине**, а
середина движется: часть «снятия» на резком ходе есть смещение полосы, а
не уход заявок. Отчёт Z2 назвал это своей главной оговоркой сам, и
починить полосой её нельзя — нужна привязка к самой цене уровня.

Отсюда прямое следствие, которое стоит держать в голове при чтении Z2:
**ноль в полосовой мере лесенку не закрывает и не подтверждает.** Полоса
не грубая версия лесенки, а загрязнённая.

Это и есть недостающий знаменатель четырёх замеров ленты T1–T4: они
видели, сколько агрессии прошло через уровень, и не видели, подставляли
ли уровень заново.

## Что меряется (объявлено ДО прогона)

Между двумя соседними снимками одного символа, по каждой цене `p`:

* `Δ = размер(p, сейчас) − размер(p, прежде)`;
* `съедено(p) = min(убыль, объём сделок НА ЭТОЙ ЦЕНЕ)`;
* `снято(p) = убыль − съедено(p)` — уровень убрали, сделок не было;
* `добавлено(p) = прирост`.

Сведённые к минуте поля (нотионал = цена × размер), по каждой стороне:

| поле | что это |
|---|---|
| `vis_b/a` | видимый нотионал пересечения — знаменатель всего |
| `eat_b/a` | съедено сделками на своих ценах |
| `cancel_b/a` | снято БЕЗ сделки на этой цене |
| `add_b/a` | добавлено |
| `dead_b/a` | нотионал уровней, ушедших в ноль без единой сделки |
| `refill_b/a` | добавлено на ценах, где в ту же минуту была сделка |
| `sweep` | съедено на базисный пункт хода середины |
| `pairs` | пар снимков в минуте; ноль — ПРОПУСК, а не нулевое наблюдение |

`dead` и `refill` — величины, невыразимые ни на свечах, ни на ленте:
заявку убрали или подставили заново, и следа не осталось нигде, кроме
записанной книги.

## Три правила, без которых мера считала бы не то

1. **Цена, ушедшая за край видимой лесенки, — не снятие.** Лесенка
   обрезана (50 уровней у альтов, 200 у BTC и ETH), и при ходе цены
   дальние уровни выпадают из видимости, не будучи отменёнными. Считается
   только ПЕРЕСЕЧЕНИЕ видимых цен двух снимков.
2. **Убыль, объяснённая сделкой на этой же цене, — не снятие.** Иначе
   «снятие» окажется переодетой агрессией.
3. **Разрыв в записи не даёт наблюдения.** Пара снимков дальше `MAX_DT`
   секунд друг от друга пропускается: иначе пятиминутная дыра станет
   гигантским «снятием» — класс дефекта из L2 (окно по номеру точки).

Каждое правило закреплено проверкой с подделкой: `test_ladder.py`,
8 блоков, пять отрицательных контролей роняют по 1–5 проверок.

## Календарь — жёсткий, и он задан диском

Лесенка живёт **только в сырье**: минутный склад Z2 её не содержит вовсе
(95 % строки снимка — это ровно то, что свёртка выбрасывает). Свободно
55.9 ГБ при приросте 4.3–5.1 ГБ/сут, то есть **11–13 суток до
заполнения**. Значит склад лесенки надо сворачивать **катящимся** —
раньше, чем сырьё состарится, — а не «когда дойдут руки».

## Цена прохода — измерена, не оценена

`out/store/Z2-ladder-bench.md`: `json.loads` на живой строке стоит
**20.0 мкс**, лёгкий разбор 3.7, регулярка по лесенке 35.8 — то есть
**json.loads быстрее собственного разбора лесенки**, и проход должен
идти им. При 51.1 млн снимков в сутки это 0.28 ч чистого разбора на
сутки записи; наблюдённые проходы проекта шли примерно втрое медленнее
арифметики, значит планировать надо около **0.7 ч на сутки записи** и
**около 18 ч на все двадцать пять**.

## Запуск

Пилот на одних сутках — он проверяет дорогу и даёт время прогона:

```bash
cd ~/algoth_v2 && git pull
```
```bash
cd ~/algoth_v2 && mkdir -p research/z3_ladder/out
```
```bash
cd ~/algoth_v2 && .venv/bin/python research/z3_ladder/fold_ladder.py --start 2026-08-24 --end 2026-08-24
```

Вся запись — отцепленно, потому что прогон длинный, а прогон в переднем
плане умирает вместе с оборвавшейся сессией:

```bash
cd ~/algoth_v2 && setsid nohup nice -n 19 .venv/bin/python research/z3_ladder/fold_ladder.py > research/z3_ladder/out/run.log 2>&1 &
```

Догон свежих суток — та же команда: готовые сутки пропускаются по
версии свёртки, читается состояние с диска, а не дельта прогона.
